# Flexible Question JSON compatibility

The Master package/manifest schema in `shared/question-import.ts` remains authoritative. Alternative JSON never reaches persistence directly. Protected Preview release is authorized; production deployment still requires separate approval.

## Pipeline and adapter registry

`parseImportSource` bounds UTF-8 bytes, JSON depth (32), value count (100,000), unsafe object keys and duplicate keys. `normalizeQuestionImport` selects an ordered, versioned descriptor from `adapterRegistry`, maps only documented equivalents, produces diagnostics and a candidate, checks source coverage, and applies the unchanged canonical validator. The browser decodes and verifies existing assets using `prepareQuestionImport`. Authenticated server validation independently repeats reviewed normalization/coverage, compares the canonical manifest, resolves actual curriculum/difficulty and signs the existing preview. Commit revalidates content, token, taxonomy, binaries, duplicate approval and transaction state before creating a draft.

| Adapter                   | Supported source                                                                                                                        |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `canonical-v1@1`          | Master `schemaVersion:1`, canonical kind, unchanged records                                                                             |
| `portable-worked-v1.1@2`  | Portable 1.1 with a structured `question.stem`, ordered worked-equation objects and inline step hints; actual supplied first-law source |
| `portable-v1.1@1`         | `format_identifier:matriculation-physics-question-portable-json`, **string** version `1.1`, documented structured profile below         |
| `aliases@1`               | Unversioned equivalent field names with recognizable question/metadata structures                                                       |
| `administrator-mapping@1` | Exact source JSON-pointer mappings, reviewed canonical corrections and explicit nonacademic metadata exclusions                         |

Unsupported versions remain blocked even if the administrator edits the candidate. An unknown unversioned identifier may be explicitly reviewed as metadata; it does not become a known portable version. Unknown arrays/wrappers enter manual mapping with source coverage; no implicit bulk import exists.

## Documented mappings

Question fields may be in a question object, at root or in metadata. Title: `title`, `question_title`, `name`; scenario: `scenario`, `stem`, `question_text`, or a **string** `question`; marks: `totalMarks`, `total_marks`, `marks`; minutes: `estimatedMinutes`, `estimated_minutes`, `estimated_time_minutes`; type: `questionType`, `question_type`, `type`; optional code: `questionCode`, `question_code`. Conflicting sources block rather than choosing priority silently.

Classification comes from explicit classification/root/metadata values: `curriculumVersionCode`, `curriculum_version_code`, `syllabus_version`; permanent `semester`; chapter/`chapter_name`; topic/`topic_name`; subtopic/`sub_topic`. No course code, approximate string match, chapter lookup or default topic assignment is inferred. Missing subtopic becomes null. Server exact parent/version resolution is authoritative. Review selectors offer all available non-retired hierarchy records without fixed counts; an administrator-approved replacement retains the original in the visible source and is explicitly not labeled a lossless classification conversion. No curriculum records change.

Difficulty uses `difficulty`/`difficulty_level`, retaining Easy/Medium/Hard across capitalization. Recognized values cannot be replaced by a different signed selection. Missing difficulty stays absent in canonical JSON and requires the separate administrator selection. An ambiguous string requires explicit confirmation and is not certified a lossless classification conversion; an invalid non-string must be corrected in source. Marks never determine difficulty.

Parts: `parts`/`subquestions`, with canonical fields or `part_id`, `parent_id`, and prompt/`question_text`/stem/string question. Nested `children`/`subparts` flatten to canonical parent links. Authored IDs, labels, relationships and marks remain; only missing local IDs, structural labels/order and actual nesting links are generated deterministically and disclosed. Missing marks are never summed or fabricated. More than 100 total parts is unrepresentable and blocked.

Schemes: `solutions`/`answer_scheme`/`marking_scheme`, either an array of structured schemes or one structured object. `partId`/`part_id` must target leaf IDs; null is used only for a no-part whole-question scheme. Solution/answer/`final_answer` is prose; `equationLatex`/`equation_latex` is raw math; teacherNotes/`teacher_notes` is private prose. Steps/`marking_steps` map ID/`step_id`, number/`step_number`, explanation/description, equationLatex/`equation_latex`/equation, working/calculation, markingPoint/`marking_point`, marks, order, markingCode/`marking_code`, blocks. Missing prose containers may be empty; missing numbers/order retain array sequence. Step marks are required. No free-text answer is converted into invented marking allocations. Multiple alternative schemes for one leaf remain unsupported; preserve compatible additional method text in explicit answer blocks or resolve the incompatibility, never discard it.

Hints: `hints`/`student_hints`, strings (question scope) or objects using canonical fields/`part_id`/`solution_step_id`/hint. Missing internal IDs and sequence are structural only. Explicit step links remain exact; links are never inferred from positions. `working_steps` is intentionally not guessed to mean hints: it may be full working and needs review. Tags/keywords must be an array. Assets/diagrams/figures must contain existing canonical embedded asset records; keyed objects can become arrays with explicit keys. URL-only assets, unplaced images or unsupported diagram structures block. No asset URL is fetched and no diagram is generated.

Balanced prose `\\(...\\)` and `\\[...\\]` become the app's `$...$` and `$$...$$`; equation bodies are unchanged. Entire wrapped raw-equation fields can be unwrapped. Paragraph blocks receive delimiter conversion; exact authored canonical packages remain unchanged. KaTeX trust stays false and Word's existing explicit unsupported-math errors remain authoritative.

## Review and preservation

The page displays detected format/version/adapter, missing required/optional fields, ambiguous/conflicting/unsupported information, mapped paths and structural defaults. Source remains read only beside an editable canonical candidate. Apply corrections explicitly before preview. JSON-pointer selectors support nested fields and root values; mapping destinations are bounded, forbid prototype keys, and cannot allocate enormous sparse arrays. Arrays may be mapped whole only when already canonical. Source leaves and supplied blocks/assets must retain their exact mapped values (except documented math delimiter conversion and explicit classification/difficulty decisions). Unknown academic values remain blocking until represented. Competing aliases require an explicit chosen destination and preservation of all supplied values.

Only designated metadata namespaces may be explicitly excluded: unknown metadata entries, importer compatibility, PDF export contract, source/reference or administrative metadata (and unknown unversioned format identifiers). Known academic paths cannot use this exemption. Exclusions are disclosed and set `lossless:false`; metadata is not injected into student content. Human review determines whether an allowed metadata field really is nonacademic. A PDF contract never controls export. Teacher notes remain private: put student-facing academic answers in answer/step blocks, not private notes.

Estimated time, title, type, marks, classification, parts with marks and structured solutions must meet the existing schema. Empty hints/tags/assets/parts and permitted textual containers are not invented academic content. No estimates, difficulty, physics values, answers, required curriculum assignments or hint text are generated.

## Security, persistence and duplicates

No new route, dependency, migration, secret, paid API or student export implementation is required. Source/candidate review exists only in browser/request memory. It is not retained as a redundant database copy. Source files should be retained by the administrator when original provenance or an old syllabus reference matters; the canonical schema has no source-provenance field.

Validation is read only. Existing admin/CSRF controls precede body handling. The canonical manifest is independently validated at preview and commit; reviewed source checks must match it. The signed plan binds selection and explicit duplicate permission. Exact structured-content fingerprints (not filenames) expose existing question IDs. A new identical preview cannot commit without separate-draft approval; retries of a successful plan still return the original ID. Rechecking inside the transaction handles questions appearing after preview. Fingerprints are structural, not a semantic similarity detector, and include curriculum/difficulty. Published records are never overwritten.

Existing atomic creation/immutable versions/receipts and asset compensation remain. No-asset imports perform zero storage calls. Generic auth, storage, transaction-failure and export regression suites remain required.

## Adding a format

1. Inspect representative real files and specify versions, semantic field structures, optional data and content that the canonical model cannot express.
2. Add a registry descriptor with a stable ID, exact detector, supported version list and canonical/portable/alias normalization mode. A version with identical semantics can share the declared profile; different semantics require an explicit typed conversion rather than merely widening the version list.
3. Extend the relevant declarative field aliases/record conversion with exact source/destination tracking, preserving all meaningful leaves. Do not weaken the Master schema, source coverage, security bounds or unknown-version guard.
4. Add positive, conflicting, missing-field, unsupported-content, malicious and source→draft→retrieval→PDF/Word tests with isolated fixtures. Include multipart/step relationships and duplicates.
5. Document the precise profile and unsupported cases. Run all quality gates, obtain release approval and test a protected deployment before production. Never use production import writes for testing.

## Actual worked-equation portable 1.1 profile

`examples/question-import/First_Law_of_Thermodynamics_MEDIUM_PORTABLE.json` is the exact user-supplied file, retained byte-for-byte with SHA-256 `ffd04d8e057c7ea666a8e205949bbb55c1c0cc12ddb4d695070bca9ba073d1f5`. It is a regression fixture, not seed content. The earlier `portable-first-law-synthetic.json` remains a separate synthetic profile fixture.

The new descriptor precedes the older portable descriptor and requires an object `question.stem`. It accepts `markdown_latex` text wrappers for stem and given conversion, `heading` as title, and `semester_display_name` as the explicit semester. Supported redundant marks/difficulty labels must agree with their source fields and map to the canonical marks/difficulty rendered by the app, avoiding duplicate labels. Empty diagram pointers/null captions indicate no diagrams; nonempty unfamiliar placements remain blocking.

Scheme `heading` maps to solution text. `given_values`, `final_answers` and `marking_allocation` retain every supplied quantity, symbol, numeric value, unit, result role, code and mark award in readable answer blocks. Their LaTeX presentations remain exact math blocks. Incomplete records and allocation/step disagreements block. Steps map `step` to number and `title` to explanation. Ordered `worked_equations` require `format:latex`, `display:true` and exact `value` bodies, with at most 100 equations per step. Inline `student_hint` text maps to a distinct hint linked to its containing source step through deterministic local identifiers. Existing conflicting blocks/separate hints are never silently replaced. Converted blocks and hint ownership are checked against subsequent candidate corrections.

`syllabus_code` retains its exact value as an academic tag. SP015 is **not** treated as a curriculum version and cannot be excluded as administrative metadata. Source identifier/provenance, subject, programme and language require explicit nonacademic review; they are never automatically converted to tags. The reviewed exclusions for the actual source are `/metadata/question_id`, `/metadata/question_source`, `/metadata/subject`, `/metadata/programme`, `/metadata/language`, `/importer_compatibility` and `/pdf_export_contract`. Reintroducing excluded provenance as tags or mapping an excluded field into the payload blocks validation in both browser and server. Academic descendants of metadata remain protected; the metadata object cannot be discarded wholesale. Importer notes and the embedded reference PDF stay outside the imported payload. The PDF is not converted to an image asset, fetched, merged into student exports or executed as instructions; the original JSON and decoded reference PDF remain verification artifacts.

The unchanged actual file lacks estimated minutes, question type, curriculum version and chapter. These remain required. The user elected to supply them later through the website. The regression fixture supplies clearly labelled test-only values in disposable local banks to exercise correction, curriculum selectors, server validation, draft persistence and exports; those values are not additions to the source file or proposed production classifications. See `REAL_WORLD_JSON_COMPATIBILITY_REPORT.md` for current readiness and verification evidence.
