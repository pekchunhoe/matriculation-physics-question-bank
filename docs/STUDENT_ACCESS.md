# Administrator-managed student access

The default delivery method is **manual email**. No domain, email-provider account, Gmail API credential, subscription or new hosted resource is needed. The original website remains the permanent Production system. Production rollout requires separate approval.

## Administrator instructions

1. Sign in with the existing administrator account and open **Student access**.
2. Add the student's email. The account remains **Pending verification**. There is a hard limit of five new registrations per Malaysia calendar day; retries of the same registration request do not count twice.
3. Choose **Generate verification link**. The link appears once, after its digest is committed. Copy it into an email addressed **only to the displayed registered email** using your existing email account. The application does not send the message. Explain that the link expires after 24 hours and that an unexpected registration can be ignored.
4. Dismiss the link and clear the clipboard after pasting. Do not open the link on the student's behalf, post it in chat, or send it through another channel. Lost links cannot be retrieved: wait one minute and generate a replacement. This immediately invalidates the earlier link. Up to five challenges per account per UTC day and 50 globally are allowed, shared with future automatic sending.
5. Refresh the status after the student confirms. Only **Verified — awaiting access code** accounts allow **Generate access code**. Copy the new code from its one-time display and deliver it privately; codes are never emailed automatically.
6. Resetting a code replaces the credential and revokes every session while preserving the student ID. Disabling an account removes its usable code and revokes sessions immediately. Reactivation requires a fresh code (and verification if not already verified). Changing email clears verification, credentials and sessions; the replacement address must verify.

Verification confirms possession of the bearer link. In this manual workflow its relationship to the registered inbox depends on the trusted administrator delivering it exclusively to that address. An administrator who opens the link can confirm it themselves; the application cannot independently attest the email delivery channel. Neither automatic email nor this workflow proves real-world identity or prevents a recipient forwarding their link.

## Student instructions

Open the link from your email and choose **Verify My Email**. Merely opening it does nothing. Successful confirmation records email verification but creates no session or access code. Wait for the administrator to give you an individual code, then sign in with the registered email and that code. Contact the administrator for registration or a replacement code; there is no public signup or reset.

The isolated Preview also requires Vercel Authentication. That is separate from the application's administrator/student sessions. Production's permanent URL remains https://matriculation-physics-question-bank.vercel.app.

## Security and persistence

- Migration `008-student-access.sql` adds students, email challenges, sessions and immutable access-event tables. Migrations 001–007 and academic records remain intact. Runtime startup requires schema 008 and never migrates automatically.
- Verification tokens contain 256 random bits, expire after 24 hours, and have only SHA-256 digests stored. Binding includes student ID, normalized email and email revision. Consumption is one write transaction; replay, expiration, regeneration and email changes invalidate inappropriate challenges.
- The HTTPS origin comes from trusted deployment configuration, never request parameters. Production uses the original URL; Preview requires its Vercel deployment URL. Links put the token in the fragment so it is absent from HTTP access logs; the confirmation page immediately removes it from history, uses self-only scripts/styles, no-referrer and no-store, and performs no third-party requests. No token/code uses browser storage or application logging.
- Link and code responses are admin-only, same-origin CSRF-protected and no-store. Ordinary listings expose neither links nor credential/token digests. Lost responses cannot be recovered; an administrator must regenerate/reset.
- Twenty random characters from a 32-character alphabet provide 100 bits of code entropy. Salted scrypt uses N=32768, r=8, p=3 (the existing vetted administrator hashing profile). Passwords are never reset by this feature. Hashing concurrency is bounded.
- Opaque 256-bit session tokens use digest-only database storage and eight-hour HttpOnly, SameSite=Strict cookies; hosted cookies are Secure and `__Host-` scoped. Every request checks account state and credential version. Reset, disable, revoke and email changes immediately reject previous sessions. Login rechecks identity/credential state inside the session-creation transaction.
- Student login has durable global, IP and account rate limits, generic credential failures and dummy hash work for missing accounts. Writes require same-origin Origin and a custom request header. All academic APIs, taxonomy, search, question details, question/answer images and PDF sources require an admin or ACTIVE verified student. Students see published material only. Existing administrator permissions remain unchanged.
- Manual generation and registration are atomic and bounded; stale revisions fail. Automatic delivery reserves a challenge, sends outside the database transaction with a provider idempotency key, then records acceptance. Failed or ambiguous delivery leaves the account pending. A previous challenge survives until the replacement is established. A two-minute lease permits recovery from an interrupted send without persisting plaintext tokens. There is no automatic retry loop.

## Optional automatic delivery (disabled)

The provider-independent adapter is retained. Real sending requires separate approval, an owned verified sending domain with SPF/DKIM and appropriate DMARC, confirmed sender identity, disabled tracking, and a server-only sending-scoped API key. Never enter credentials in chat or Git. `STUDENT_EMAIL_PROVIDER=resend`, `RESEND_API_KEY`, `STUDENT_EMAIL_FROM` and `STUDENT_EMAIL_DOMAIN_VERIFIED=true` enable the adapter only after those checks. No provider was connected and no real automatic email was sent during development.

At five registrations per day, approximately 150 initial emails/month plus resends fit Resend's published Free allowance of 3,000/month and 100/day. Email service cost would be US$0 within that tier; domain purchase/renewal would be a separate quoted cost. Postmark's Free tier is 100/month, below 150/month; its Basic plan starts at US$15/month for 10,000 emails. Manual delivery adds no application email-service charge and remains subject to the user's existing mailbox limits.

1. Complete isolated Preview validation first, including actual controlled-inbox manual delivery. Preserve its encrypted pre-008 backup and migration/source fingerprints, test evidence and deployed SHA. Confirm private Blob/Turso isolation and Vercel Authentication before hosted writes.
2. Review remote Git divergence and automatic deployment triggers. Production is based on `69cc4dbd66da88c044d2b23a04bf5adc7fcef9ce`; do not push or merge simply to synchronize branches. Deploy the reviewed local commit to only the existing testing project through the supported Preview CLI flow.
3. After separate Production approval, establish a short write freeze and capture a fresh consistent encrypted backup of the ORIGINAL Production database at schema 007. Restore it locally and compare every logical table, schema object, administrator credential fingerprint, foreign keys and integrity. Snapshot original deployment/domain/environment and private Blob inventory. Verify all existing image references are readable with the original storage binding. Never replace Production with the disposable database/store.
4. Under the same controlled freeze, rehearse and then apply **only 008** to the original database. Production already has migrations 006 and 007; do not replay them. Compare all prior rows and old migration records, check foreign keys/integrity, and confirm new tables are empty. Keep the original administrator email/password unchanged.
5. Deploy the exact tested application commit to the ORIGINAL Vercel project with its original Turso, Blob and domain bindings. No migration to a second permanent website. Verify initialization, security headers, administrator login, anonymous academic denial and private-image authorization.
6. Register one approved real student; manually email the one-time link; confirm no access before verification and administrator code issuance. Verify student login, published questions, matching answer images and PDF exports. Verify an administrator can still upload a question/answer pair with optional Subtopic, publish it and retrieve it as a student.
7. Before release, agree on rollback behavior: the previous application permits anonymous academic access, so blindly reverting it would undo the privacy requirement. Prefer a protected maintenance response while fixing forward. An authorized code rollback may use the previous schema-007 application against the additive schema only after verifying its strict startup schema check (the current old runtime rejects schema 008). Restoring the verified pre-008 backup requires an approved write freeze, preservation/export of any new student/academic writes, and explicit acknowledgement of data-loss risk. Restore only the ORIGINAL database, never the testing database. Keep original image objects; avoid destructive schema rollback scripts.
8. After recovery, recheck database integrity, administrator login, original domain/deployment/bindings and image inventory before reopening. Record the outcome and revoke temporary validation sessions without changing administrator passwords.

Until these gates are satisfied, this is not a Production rollout approval or a claim of actual inbox delivery.
