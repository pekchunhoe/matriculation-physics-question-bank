# Flexible importer: architecture audit and design

Audited 11 October 2026 before implementation. Work is local only; no deployment or production data writes are authorized by this request. The pending three-file CSP font correction is unrelated existing work and is preserved.

## Existing pipeline

- `shared/question-import.ts` is the authoritative strict Zod v1 package/manifest contract; `shared/schema.ts` defines persisted parts, marking steps and hints; `shared/content.ts` validates prose, safe KaTeX and ordered content blocks.
- `src/QuestionJsonImporter.tsx` accepts one file or pasted JSON. `src/question-import-preparation.ts` currently parses JSON and immediately applies the canonical package schema. It splits embedded bytes from the manifest and verifies lengths/hashes locally. There is no format detection or normalization.
- `server/app.ts` authenticates privileged requests and checks same-origin CSRF before parsing import payloads. `server/question-json-import.ts` revalidates the strict manifest, resolves exact non-retired curriculum names and administrator-selected difficulty, signs a 15-minute preview bound to content/admin/taxonomy, and revalidates on commit.
- Commit verifies every image before storage writes, uses `Bank.transaction` / `createInTransaction`, creates a draft plus immutable version/classification and `question_import_receipts`, and compensates newly owned unlinked uploads on failure. Receipt retries are idempotent. A new preview of identical content currently warns but permits duplicates without separate approval.
- Current source `difficulty` is legacy metadata deliberately ignored in favor of a separate administrator selection. This behavior must change to meet this request's source-difficulty preservation requirement.
- Curriculum mapping is exact under version/semester/chapter/topic; permanent semester names are Semester 1/2. No fixed topic counts are used. Retired source classifications cannot currently be imported and must be reviewed against an available curriculum; no taxonomy mutation is needed.
- Parts are a flat adjacency list (`id`, `parentId`, `label`, `prompt`, `marks`, `order`, optional blocks). Schemes target exactly one leaf; no-part questions require a whole-question scheme. Parent marks equal direct children; root marks and scheme-step allocations equal total marks. Hints optionally target explicit step IDs. Arbitrary alternative solutions cannot be represented as extra schemes for the same part and must be blocked rather than dropped.
- Required question fields: title, scenario (may be empty with other content), positive integer totalMarks and estimatedMinutes, one supported questionType. Estimated time is **required** in the existing schema; it cannot be invented. Classification requires version code, permanent semester, chapter, topic and nullable subtopic. Arrays parts/hints/tags/assets may be empty; solutions cannot. Scheme/step empty textual fields are valid but marks and relationships must remain valid. Question code, blocks, difficulty, step IDs/marking codes, step-hint linkage and asset alt/caption are optional.
- Asset import supports at most eight supplied PNG/JPEG/WebP/safe SVG images with exact Base64/length/SHA-256/placement. No external asset fetching. Existing image service handles privileged storage and draft privacy. No diagram generation.
- `src/MathText.tsx` and `src/word-export.ts` use dollar-delimited inline/display math; raw equationLatex uses KaTeX. Compatibility conversion can translate balanced `\\(...\\)` / `\\[...\\]` delimiters to supported delimiters without altering equation bodies. No rendering changes are needed.
- `shared/export-content.ts`, `shared/export-plan.ts`, `src/word-export.ts`, `src/word-math.ts` and browser export tests provide device-side PDF and native OMML Word exports. Export contracts in source JSON are not authority.
- Existing fixtures: dimensional-analysis, synthetic-visual and GOLDEN_QUESTION_IMPORT_REFERENCE under `examples/question-import`; import, fidelity, storage, auth, export and browser tests use disposable SQLite/libSQL. No actual First_Law_of_Thermodynamics_MEDIUM_PORTABLE.json was found in the repository or attachment inventory. A clearly labeled synthetic portable fixture will demonstrate a documented supported profile; it cannot certify compatibility with an unavailable file.

## Design before implementation

Add a shared deterministic, versioned compatibility engine: bounded safe parse → detect canonical/portable-v1.1/alias/unknown → normalize → loss/ambiguity diagnostics → unchanged canonical validation. Keep the canonical adapter exact. Support only explicit unambiguous aliases and structural profiles; unsupported versions and meaningful fields without a destination block import. Record original and canonical paths and administrative defaults. Generate only structural identifiers/order, never academic content, marks, difficulty, time or classification.

Provide browser review of source versus candidate, field-path mapping, administrator corrections, and explicit designation of nonacademic metadata. Never mark acknowledged omissions lossless. Unknown structures enter manual review rather than receiving fabricated values. Server invokes the same bounded engine for alternative manifests and independently validates canonical data at both existing write boundaries. Normalization has no database, network or expression execution.

Use existing receipts/fingerprints to identify duplicate questions, expose existing IDs and require a signed explicit separate-draft choice; recheck inside the write transaction. Preserve strict auth, CSRF, asset security, taxonomy snapshots and revision logic. No migration, new dependency, paid service or student export change is planned.
